# **SPEC: Rules file & Rules engine · v1.0 · 14 Nov 2026, 13:45 (Baku)**

## **0\. In simple terms**

The module determines the indicator’s color (green, yellow, or red) and what the astronaut should do next. It works like a “doctor following instructions”: it reads the `rules.json` file and assigns a color strictly according to it. It doesn’t come up with anything on its own, and there are no AI inside it. The rules file was compiled manually from the Ayesha table. Each rule consists of a single sentence from the YELLOW or RED columns, converted into numbers, with its source indicated next to it. The module receives as input measurements from the past few days, checked-off symptoms, and the astronaut’s personal baseline (calculated by the adjacent “Personal Baseline” module). The output for each metric includes: a color, which rules were triggered, a brief explanation, recommended actions, and who to contact (the astronaut themselves → the crew medic → a doctor on Earth). In the Day 40 story, it is this module that turns heart rate and sleep yellow and suggests what to do. A separate file, `knowledge_base.json` (all 16 rows of the table as text), serves only as a reference for the AI assistant and the “Learn more” screen; it never determines the color.

## **1\. Goal**

Turn validated measurements, ticked symptom flags and the astronaut's personal baseline into a deterministic status (green / yellow / red / no data) per indicator, with the triggered rules, explanation, actions and escalation level, using only `src/data/rules.json`.

## **2\. Context**

* **Inputs come from:** the Storage module (readings history), the check-up form (today's flags), the Baseline module (personal norms). None of these modules has a spec yet \[ANSWER: Lana, Q2\]. **This spec defines the contract they must follow** (section 4).  
* **Outputs go to:** the body map and indicator cards (colour, texts), the Earth window (red → message to the flight surgeon), and the AI helper (list of triggered rules; the AI may explain them but may not change colour or urgency \[BRIEF §6\]).  
* **Not here:** plausibility checking (Input validation module) and baseline calculation (Baseline module) \[BRIEF §5\].  
* **Challenge questions supported** \[BRIEF §1\]: Q4 "when does a result need crew or ground attention" (yellow → crew, red → ground); Q5 "what actions prevent a critical condition" (actions per rule). Judging criteria: scientific validity (every rule has a source), relevance, impact.

## **3\. User scenarios**

**S1 — Day-40 demo (heart and sleep)** \[BRIEF §4\]

1. Morning check-up: the astronaut enters heart rate, sleep and mood and ticks no flags.  
2. Input validation has already rejected "920 bpm", so the engine never sees it.  
3. The engine compares heart rate with the preflight baseline. Rule `hr_y_baseline` fires → heart **yellow**, escalation `crew_medical_officer`. *(Rule is disabled until OPEN QUESTION Q-HR is answered; see §12.)*  
4. Sleep 7-day average is below 7 h → `sleep_y_avg7` → sleep **yellow**.  
5. The card shows title, explanation, actions and recheck time. The overall status is yellow.

**S2 — Red flag.** The astronaut ticks "Swelling of the face or throat" → `imm_r_flags` → immune **red**, escalation `ground_flight_surgeon` → the Earth window module is notified (out of scope here).

**S3 — First days.** Day 2 of the mission, rolling baseline has 1 reading. Baseline-dependent rules are skipped with reason `no_baseline`. Absolute rules still run. The card shows "Your personal baseline is still forming…".

**S4 — Nothing measured.** No reading and no flag for skin today → skin `no_data`.

## **4\. Inputs and outputs (data contract)**

Language: **TypeScript** \[ANSWER: Lana, Q4: React\]. Dates are local mission dates `YYYY-MM-DD` (strings). One check-up per day.

### **4.1 Types (put in `src/rules/types.ts`)**

```ts
export type Level = "green" | "yellow" | "red";
export type Status = Level | "no_data";
export type Escalation = "self" | "crew_medical_officer" | "ground_flight_surgeon";
export type Op = "<" | "<=" | ">" | ">=";
export type MeasurementContext = "rest" | "exercise";

// ---------- INPUT ----------
export interface Reading {
  date: string;                 // "2026-11-14", required
  metric: string;               // must be a metric id from rules.json, e.g. "heart_rate"
  value: number;                // in the metric's unit from rules.json
  context?: MeasurementContext; // default "rest"; only body_temp uses "exercise" in v1
  valid: boolean;               // set by Input validation; engine ignores valid=false
}

export interface Baseline {
  preflight_mean: number | null; // from synthetic preflight data
  preflight_sd: number | null;
  rolling_mean: number | null;   // mean of previous N days (N = settings.rolling_baseline_days), today EXCLUDED
  rolling_sd: number | null;
  rolling_n: number;             // how many valid readings went into rolling_mean
}

export interface EvaluationInput {
  today: string;                       // "2026-11-14"
  readings: Reading[];                 // history incl. today, any order; engine sorts
  flags: string[];                     // flag ids ticked in TODAY's check-up
  baselines: Record<string, Baseline>; // key = metric id; missing key = no baseline
  rules: RulesFile;                    // parsed src/data/rules.json
}

// ---------- OUTPUT ----------
export interface TriggeredRule {
  rule_id: string;
  level: "yellow" | "red";
  source: string;            // copied from rules.json
  title: string;
  explanation: string;
  actions: string[];
  recheck: string;
  observed?: {               // what caused it, for the UI and the AI helper
    metric?: string;
    value?: number;          // today's value (or window average)
    baseline?: number;       // baseline mean used, if any
    delta?: number;          // value - baseline (abs), % or SDs, matching trigger.unit
    flags?: string[];        // flags that matched
  };
}

export type SkipReason =
  | "rule_disabled" | "no_reading_today" | "no_baseline"
  | "insufficient_history" | "missing_flags";

export interface SkippedRule { rule_id: string; reason: SkipReason; }

export interface IndicatorResult {
  indicator_id: string;           // e.g. "heart_rate"
  status: Status;
  escalation: Escalation | null;  // null when status = "no_data"
  triggered: TriggeredRule[];     // red first, then yellow, then rules.json order
  skipped: SkippedRule[];
  baseline_forming: boolean;      // true if ≥1 rule skipped with "no_baseline"
  pending?: PendingRule[];        // rules met TODAY whose persistence is not yet reached (info only, never changes status)
}

export interface EvaluationResult {
  today: string;
  overall_status: Status;          // worst of indicators; "no_data" only if all are no_data
  overall_escalation: Escalation | null;
  indicators: IndicatorResult[];   // same order as rules.json
  rules_version: string;           // rules.schema_version
}
```

### **4.2 Rules file structure (`src/data/rules.json`, already drafted)**

```ts
export interface RulesFile {
  schema_version: string;
  settings: { rolling_baseline_days: number; min_rolling_baseline_readings: number };
  escalation: { green: Escalation; yellow: Escalation; red: Escalation };
  ui_text: Record<string, string>;
  metrics: { id: string; indicator_id: string; label: string; unit: string;
             plausible_min: number | null; plausible_max: number | null }[];
  flags: { id: string; kind: "symptom" | "event"; indicator_ids: string[]; label: string }[];
  indicators: { id: string; label: string; table_confidence: string; rules: Rule[] }[];
}

export type Trigger =
  | { type: "threshold";      metric: string; op: Op; value: number | null; context?: MeasurementContext }
  | { type: "baseline_delta"; metric: string; baseline: "preflight" | "rolling";
      direction: "above" | "below" | "either"; unit: "abs" | "percent" | "sd";
      amount: number | null; context?: MeasurementContext }
  | { type: "window_average"; metric: string; days: number; op: Op; value: number }
  | { type: "flag";           flags: string[] };

export interface Rule {
  id: string; level: "yellow" | "red"; enabled: boolean;
  trigger: Trigger;
  persistence: number | null;   // consecutive days the condition must hold, ending today
  requires_flags: string[];     // if non-empty: at least ONE of these must be ticked today
  source: string; title: string; explanation: string; actions: string[]; recheck: string;
}
```

`plausible_min/max` are stored here for the Input validation module, which reads them. This engine does not use them.

## **5\. Logic and rules**

### **5.1 Loading**

`loadRules(json: unknown): RulesFile` validates the structure by hand (no schema library) and throws `RulesFileError` with a readable message if:

* a required field is missing or has the wrong type;  
* rule ids are duplicated;  
* a trigger references an unknown metric or flag;  
* an **enabled** rule has `null` in `value`, `amount` or `persistence`.

`rules.json` is imported at build time (`import rules from "../data/rules.json"`), never fetched over the network.

### **5.2 `evaluate(input: EvaluationInput): EvaluationResult` — pure, deterministic function**

Preparation:

1. Drop readings with `valid === false` and readings with `date > today`.  
2. For each metric and date, keep one reading per context. If there are several, keep the **last one in array order**.  
3. Define `day(k)` \= the date k days before `today` (calendar days; `day(0) = today`).

For each indicator, for each rule (in file order):

| Step | Check | If it fails → skip reason |
| ----- | ----- | ----- |
| a | `enabled === true` | `rule_disabled` |
| b | evaluate the trigger (5.3) | its own reason, or "not met" (not listed as skipped) |
| c | if `requires_flags` is non-empty: at least one of them is in `input.flags` | not met (no skip entry) |

### **5.3 Trigger types**

Let `P = persistence ?? 1` and `ctx = trigger.context ?? "rest"`.

1. **threshold:** for every k in 0..P-1 there is a reading of `metric` with context `ctx` on `day(k)`, and `compare(value, op, trigger.value)`is true.  
   * No reading on `day(0)` → skip `no_reading_today`.  
   * A reading missing on any `day(k)`, k ≥ 1 → skip `insufficient_history`.  
2. **baseline\_delta:** pick the baseline:  
   * `preflight` → use `preflight_mean` and `preflight_sd`; available if `preflight_mean !== null`;  
   * `rolling` → use `rolling_mean` and `rolling_sd`; available if `rolling_n >= settings.min_rolling_baseline_readings`.  
3. If the baseline is not available → skip `no_baseline`. Then compute `delta` for each k in 0..P-1 (the same baseline for all k):  
   * `abs`: `value − mean`  
   * `percent`: `(value − mean) / mean × 100`  
   * `sd`: `(value − mean) / sd`; if sd is null or 0 → skip `no_baseline`  
4. The condition is met when, for all k: `above` → `delta >= amount`; `below` → `−delta >= amount`; `either` → `|delta| >= amount`. Missing readings are handled as in threshold.  
5. **window\_average:** needs a reading on each of `day(0)`..`day(days−1)`. Otherwise skip `insufficient_history` (or `no_reading_today`if `day(0)` is missing). Met if `compare(mean(values), op, value)`. `persistence` is ignored.  
6. **flag:** met if any id in `trigger.flags` is in `input.flags`. `persistence` is ignored (flags are today-only). Never skipped.

Comparisons use plain JavaScript numbers. **No rounding** before comparing.

### **5.4 Indicator status**

1. If at least one rule triggered: `status` \= the highest level among them (red \> yellow).  
2. Else, if the indicator **has metrics** in `rules.metrics` (`indicator_id` match): `green` if there is at least one valid reading of any of its metrics dated `today`, otherwise `no_data`.  
3. Else (indicator has **no metrics**, in v1 only `immune_signs`): `green`. ASSUMPTION A8: a submitted check-up with no ticked flags means "none of these symptoms".

Further rules:

* `escalation = rules.escalation[status]` (`null` for no\_data).  
* `baseline_forming = skipped.some(s => s.reason === "no_baseline")`.  
* Overall status \= the worst over indicators, ordered red \> yellow \> green \> no\_data.  
* The engine **never** lowers a level. A personal-baseline rule can only add warnings; absolute thresholds always apply \[ANSWER: Lana, approved 12:33 explanation\].

### **5.5 Edge cases**

| Case | Behaviour |
| ----- | ----- |
| `readings` empty, `flags` empty | every indicator with metrics `no_data`; `immune_signs` `green` (A8); overall `green` |
| Invalid reading (valid=false) | ignored as if absent |
| Reading for an unknown metric | ignored, no error |
| Unknown flag id in `input.flags` | ignored, no error |
| Baseline mean \= 0 with unit `percent` | skip `no_baseline` |
| Rule disabled (open question) | skip `rule_disabled`. The UI does not show it. |
| Conflicting signals (yellow and red on one indicator) | red wins; both listed in `triggered` |
| Same input twice | identical output (deep equal) |

## **7\. Security and privacy**

* `rules.json` and `knowledge_base.json` are bundled at build time; there is no network access in this module.  
* No `eval`, no `new Function`, no dynamic code from the rules file. Rules are data, interpreted by a fixed `switch` on `trigger.type`.  
* Every text from the rules file is rendered as plain text (React default); never `dangerouslySetInnerHTML`.  
* The engine accepts only finite numbers: a reading with `!Number.isFinite(value)` is treated as invalid.  
* No logging of health values to the console in production builds.  
* No secrets are involved. The module has no dependencies outside the TypeScript standard library.

**Radiation measurement note (Q-RAD, 15 Nov 2026).** Both radiation fields are read every day from the crew member's personal active dosimeter, and both are needed:

- `radiation_dose_rate` (µSv/h) — the dose rate *right now*. It catches sudden spikes (a solar particle event can raise it many times within hours). Nominal Mars-transit cruise ≈ 75 µSv/h. Rule: `rad_y_rate` (> 150 µSv/h → yellow).
- `radiation_accumulated` (mSv) — the total since mission start, read from the dosimeter. It is compared with the 600 mSv NASA career limit. It grows slowly (≈ 1.8 mSv/day). Rules: `rad_y_accum` (≥ 480 → yellow), `rad_r_accum` (≥ 600 → red); also feeds the Dose budget meter.
- One cannot replace the other: a once-a-day rate reading is a snapshot and cannot be integrated into a total (an event at night between check-ups would be missed), and the slow-growing total hides short spikes.
- **Units (simplification):** a dosimeter physically measures *absorbed dose* in grays (mGy, µGy/h). *Dose equivalent* in sieverts adds a weighting for the biological effect of the particle type (in deep space the heavy ions make it roughly 3–4 × the absorbed dose). NASA's limit and the MSL/RAD cruise figures are in sieverts, so the app uses µSv/h and mSv and assumes the dosimeter software has already converted Gy → Sv. Suggested answer if asked: "Values are dose equivalent; on a real instrument the conversion from grays is done by its software."
